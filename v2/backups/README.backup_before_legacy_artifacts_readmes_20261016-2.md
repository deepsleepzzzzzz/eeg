## 逐条缺陷记录

### v1 · 符号化尺度 bug（结果不可用）

```
分位边界在【z-score 尺度】上拟合，却拿去切【原始幅值】的数据。
后果：6 档里每个窗只用到 2 档 → 6×6 转移矩阵退化成 2×2。
```
- 影响：齿轮准确率被压在 95% 左右（修复后同协议达 98.7%）
- 修复：commit `fbe2ca9`（`build_state_transition` 先做与拟合一致的预处理）
- 防复发：`tests/test_bin_edges_scale.py`（3 项回归测试）
- **这 40 组数字不得用于任何结论。**

### v2 · GCN 的 `gcn_steps` 与滞后阶数不符（GCN 语义有缺陷）

```
v2 协议: 通道=3  滞后=7  gcn_steps=3      ← 3 ≠ 7
relational 布局要求 gcn_steps == 滞后数；
21 个矩阵被按 (7 通道, 3 步) 拆分组，而正确拆法是 (3 通道, 7 步)。
```
- 影响：**CNN 的 20 组不受影响**；GCN 的 20 组虽然数值正常，
  但"每个滞后是一个独立关系"这一说法对它不成立。
- 修复：commit `d698425`（v3 起 `gcn_steps` = 滞后数）
- 防复发：`tests/test_protocol_structure.py::test_gcn_steps_equals_number_of_lags`
- 加上前面那个符号化 bug，v2 的 GCN 结果建议不引用。

### v3 · 8 通道（不采用）

SEU 官方 README 只明确背书"第 2、3、4 行（行星齿轮箱 xyz）有效"。
v3 用了全部 8 个通道，虽然数字最高（齿轮 100.00%），但通道选择缺乏官方依据，
审稿人可能质疑。v4 起回到 3 通道。

## ⚠️ 一个共同的局限

**这 160 组历史结果，全部产生于"审计还不存在、或审计还在审错协议"的时期。**
上表的检查是**事后结构核对**，它能证明：
- ✅ 每个 run 记录的分割指纹 = 它协议缓存的指纹
- ✅ 每个 run 的 manifest 确实指向它声明协议的缓存
- ✅ 缓存形状与符号化档位符合协议声明

**它证明不了**：当时的训练流程与现在是否逐位一致。
所以对历史结果，只能做"结构上可信"的结论，不能做"逐位可复现"的结论。
